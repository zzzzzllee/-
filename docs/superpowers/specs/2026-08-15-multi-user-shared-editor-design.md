# 2026 级招新推文：多人共享在线编辑设计

日期：2026-08-15

## 目标

将当前“浏览器本机草稿 + 发布到 GitHub”的编辑方式，改为多人共享在线编辑：多人打开同一个编辑链接，可以同时修改文字、图片、二维码和宣传片配置；修改自动保存到云端，关闭电脑或刷新页面后仍然显示最新版本，不再需要上传 GitHub。

## 推荐方案

使用 Supabase 作为独立云端数据服务，GitHub Pages 只负责托管页面文件：

- Postgres：保存当前推文内容 JSON、版本号和更新时间。
- Storage：保存在线编辑上传的图片文件，返回可访问图片地址。
- Realtime：把一位编辑者的保存结果实时推送给其他打开页面的人。
- Supabase anon key：只放在网页端，用于访问公开内容和共享编辑接口；不使用 GitHub 账号密码。

纯 GitHub Pages 是静态托管，不能直接提供多人共享数据库。因此要实现“保存后重新打开仍是最新内容”，必须增加一个云端数据服务。

## 编辑权限

采用共享编辑链接，不要求账号登录：

```text
https://zzzzzllee.github.io/-/editor.html?share=一段随机共享密钥
```

拿到共享编辑链接的人可以编辑；普通首页链接只读展示。共享密钥可以在设置中重新生成，重新生成后旧编辑链接失效。

这是“链接即权限”的模式：不需要账号密码，但不要把编辑链接公开发布到不可信群组。如果以后需要严格区分每个人的权限，再增加登录功能。

## 数据流程

1. 首页打开时从 Supabase 读取最新内容；读取失败时临时回退到仓库里的 `content.json`。
2. 编辑器打开时使用共享链接读取同一份内容。
3. 文字输入停止约 600 毫秒后自动保存到云端。
4. 图片选择后立即在浏览器中预览，同时上传到 Supabase Storage；上传完成后保存图片 URL。
5. 其他编辑器通过 Realtime 收到更新并刷新相应字段。
6. 页面刷新、关闭电脑或换手机后重新读取云端内容，显示最后一次成功保存的版本。
7. 不再显示“保存并同步到 GitHub”按钮；保留本机 IndexedDB 作为断网临时草稿。

## 并发策略

第一版采用“字段级合并 + 同一字段最后保存者优先”：

- 不同人同时修改不同文字字段时，互不覆盖。
- 同一文字字段同时修改时，以最后一次成功保存为准。
- 图片以图片键为单位保存，替换一张图片不会覆盖其他图片。
- 页面显示最近更新时间和“已同步 / 正在同步 / 断网草稿”状态。

这满足多人同时编辑推文的实际需求，但不是 Google Docs 那种逐字光标级协作；如后续需要逐字协作，再升级为 CRDT。

## 安全与限制

- 不保存 GitHub 登录密码，也不要求编辑者登录 GitHub。
- Supabase 项目 URL 和 anon key 可以公开放在页面中；服务端表规则只开放必要的内容读写。
- 图片桶使用公开读取、受共享链接控制的上传接口。
- 共享链接泄露即代表编辑权限泄露，支持重新生成共享密钥。
- 不能把 Supabase service-role key 放进网页；后台密钥只能留在服务端或部署环境变量中。

## 需要的一次性配置

实现并上线前，需要一个 Supabase 项目的：

- Project URL
- anon public key
- 一个用于图片的 Storage bucket
- 一张推文内容表

这些不是 GitHub 账号密码。没有 Supabase 项目时，可以先完成页面和配置文件，接入后再启用云端保存。

## 验收标准

- 两台设备同时打开共享编辑链接。
- 设备 A 修改文字后，设备 B 能自动看到更新。
- 设备 A 上传图片后，设备 B 刷新页面能看到新图片。
- 关闭电脑后，用手机重新打开仍能看到最后保存的版本。
- 页面不再要求 GitHub Token，不再上传 `content.json` 到 GitHub。
- Supabase 暂时不可用时，编辑器仍能使用 IndexedDB 保存本机草稿，并提示云端同步失败。
